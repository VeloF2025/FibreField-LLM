# FNO Coverage Data Scraper System – Product Requirements Document

**Overview:** This PRD describes an internal system for Blitz Fibre / Velocity Fibre to gather and utilize fibre network operator (FNO) coverage data. The system will scrape coverage information from multiple FNO websites, normalize and store it in a spatial database, and provide tools (APIs and a web UI) to query and visualize which addresses or areas are fiber-covered. The goal is to equip support, sales, and planning teams with up-to-date coverage insights across all partner FNOs. Key features span from a robust scraping infrastructure and data pipeline to a user-friendly mapping interface and future integrations. The following sections detail each component of the system.

## 1. Scraping Infrastructure

The system will employ a **modular, plugin-based web scraping engine** to handle multiple FNO sources. Each FNO’s scraping logic will be encapsulated in its own “plugin” or module, making it easy to add new FNOs or update existing ones without affecting the whole system. Depending on the target site’s complexity, different scraping frameworks can be used:

- **Scrapy for Static Content:** For FNO websites that serve coverage data via static HTML or simple requests, Scrapy is ideal. Scrapy is a fast, powerful Python framework specifically for web crawling and data extraction【47†L17-L24】. It excels at handling large numbers of pages and follows links automatically. However, Scrapy alone cannot execute client-side JavaScript【12†L1-L4】, so it’s best suited for sites where data can be obtained from HTML or known API endpoints.
- **Headless Browser for Dynamic Content:** If an FNO’s site loads coverage maps via heavy JavaScript (for example, an interactive map), a headless browser approach will be used. This could involve **Playwright** or **Selenium**. Selenium can drive a real browser (Chrome, Firefox, etc.) and thus **can run JavaScript and interact with dynamically loaded websites**【11†L367-L375】. Playwright is a newer alternative, offering multi-browser support and faster execution than Selenium in many cases【11†L273-L281】【11†L285-L293】. The scraping plugin for such a site might use Playwright’s Python integration or Selenium with an “undetected” Chrome driver to avoid bot detection【10†L1-L4】. These tools will emulate user interactions needed to retrieve coverage data (e.g. clicking map tiles or loading results).
- **Direct API Access:** If an FNO provides an unofficial or public API endpoint for coverage queries (some FNOs have an address lookup API or publish coverage polygons via endpoints), the scraper will call those directly. This is more efficient and reliable when available, as it avoids any complex page rendering.

Each plugin will therefore choose the appropriate method (Scrapy spider, or a Playwright/Selenium script, or direct HTTP calls) to obtain coverage data from that FNO. The **plugin interface** will standardize how results are returned (e.g. yielding coverage records in a common format) so that downstream processing is uniform.

**Anti-Scraping Measures:** To ensure the scrapers run reliably at scale, the system will implement robust anti-blocking and stealth techniques:

- **IP Rotation:** The scraper infrastructure will rotate IP addresses or use a pool of proxy servers to distribute requests. This prevents overwhelming any single target and avoids simple IP-based blocking. In practice, IP rotation means switching between many IPs so that your traffic is spread out【8†L1-L4】. By appearing to come from different addresses (including residential or geo-distributed proxies if needed), the scrapers reduce the risk of being flagged by rate-limit or bot-detection systems.
- **User-Agent Spoofing and Rotation:** Scraper requests will include randomized or varying User-Agent headers to mimic different browsers/devices. Using a real browser’s User-Agent string and cycling through multiple options helps disguise the scraping as ordinary user traffic【9†L1-L4】. The system will maintain an updated list of common User-Agent strings (Chrome, Firefox, mobile Safari, etc.) and assign them per request or per session.
- **Headless Browser Evasion:** When using headless browsers, the system will employ techniques to avoid detection. Many anti-bot systems look for telltale signs of automation like the standard _HeadlessChrome_ user agent or missing browser APIs. Tools like **undetected-chromedriver** (and its successor **Nodriver**) patch the browser automation to remove headless fingerprints, helping to bypass anti-bot scripts【10†L1-L4】. Additionally, the scrapers can enable stealth options (e.g. in Playwright’s launch arguments or using browser plugins) to appear more like a real user (randomizing navigator properties, enabling graphics, etc.).
- **Throttling and Random Delays:** The scraping engine will be polite in how it crawls FNO sites. It will throttle its request rate and include random delays between requests (e.g. jitter between 1-10 seconds) to simulate human browsing patterns. As a best practice, **not sending requests in a perfectly steady rapid stream** makes the activity less conspicuous【6†L517-L525】【6†L534-L543】. The system may also implement adaptive backoff – if a site responds with a 429 Too Many Requests or starts slowing responses, the scraper will pause or slow down further【6†L551-L560】【6†L543-L550】. This avoids overloading the FNO servers and reduces the chance of IP bans.
- **CAPTCHA Handling:** In case any target site uses CAPTCHA challenges (some FNO portals might trigger a CAPTCHA if they suspect automation), the system will have a strategy to handle it. Where possible, using **Playwright’s built-in solutions or external captcha-solving services** can solve CAPTCHA prompts【6†L473-L481】【6†L485-L494】. However, the preference is to avoid CAPTCHAs entirely by staying under detection thresholds.
- **Session & Cookie Management:** Scrapers will manage cookies and possibly login sessions (if the data requires authentication or a postcode form submission) so that repeated queries can reuse sessions similar to a regular user browsing multiple pages. This includes handling any tokens or required headers.

The scraping infrastructure will be **extensible**. New FNOs can be added by writing a new plugin module adhering to a common interface (e.g. a Python class with methods like `fetch_coverage()` that returns data in the unified schema). This plugin-based approach ensures that as the company adds support for more South African FNOs or even international ones, development remains modular and maintainable. Each scraper plugin can be developed and tested in isolation.

In summary, the scraping component is **flexible (supports multiple frameworks), stealthy (implements anti-detection best practices), and modular (one plugin per FNO)**. It will be deployed in a scalable way (discussed in section 4 and 5) to routinely gather fresh coverage data.
